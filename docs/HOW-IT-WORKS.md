# 原理与踩过的坑

README 讲怎么用，这里讲**为什么这么写**。如果你想自己实现一遍，或者哪天工具坏了要排查，看这份。

所有结论都来自实测，标注了日期。没实测过的地方会写明是推测。

---

## 一、为什么必须在「阅读器页」里请求

> 这是最容易卡住的一条，作者在这上面耗了两个多月。

`/web/mp/articles` 这个接口，**在微信读书首页请求一定失败**，返回 `-2041`；在阅读器页（`/web/mp/reader/<hash>`）里请求同样的 URL，就正常返回。

推测是 Referer 校验，或者页面加载的 WASM 模块参与了请求签名。没有深挖，因为知道「必须在阅读器页里发」就够用了。

**当时的误判过程值得记一下**：作者把 `-2041` 当成了「账号被限流」，于是换小号验证——小号也是 `-2041`，于是判定「接口对所有账号关闭了，这条路死了」，差点放弃整个方案。

实际上**八次失败都是同一个调用错误**。

真正戳破它的是一句话：「我手动在浏览器里能看到文章啊。」

> **判据**：当「你手动能访问、程序访问不了」时，先怀疑自己的调用方式，而不是对方封禁。用 `performance.getEntriesByType("resource")` 看看页面自己发的请求长什么样，跟你发的比一比——差异通常就在**发起页面**、请求头或参数上。

## 二、`innerText.length` 不能拿来判断页面好坏

很自然会想：「正文只有十几个字 = 白屏 = 出问题了」。

**这是错的。** 2026-08-04 实测，阅读器页**完全正常、能抓到 138 篇文章**的时候：

```
document.body.innerText  →  "微信读书书城 XXX 首页 我的书架"   （18 个字）
```

文章列表根本不进 `innerText`。所以**健康页面和白屏页面在长度上完全一样**。

> ✅ 正确判据是 `document.title`：渲染好了会变成「XXX - 公众号 - 微信读书」，没好就停在「微信读书」。

这条坑之所以危险，是因为「18 个字 = 白屏」这个结论在只观察故障情况时看起来完全成立——你只有在正常时也去量一次，才会发现它是假的。

## 三、验证码：三个陷阱

页面会弹腾讯防水墙（TCaptcha）的验证码，图片点选或滑块。工具的做法是**发现 → 停下 → 交给用户 → 自己确认真的好了 → 继续**。识别和点选不做，那是绕过人机校验。

自动**识别**这件事不做，但自动**判断有没有**必须做对，否则整条流程要么白等要么误判。这里有三个陷阱，全是实测撞出来的：

### 陷阱一：写死的精确 id 匹配不上

很多资料会说 TCaptcha 的节点是 `#tcaptcha_iframe`。实测（2026-08-04）不是：

```
DIV     id=tcaptcha_wrapper_transform_dy   class=tcaptcha-transform   362×362
IFRAME  id=tcaptcha_iframe_dy              src=captcha.gtimg.com/...  360×360
```

**真实 id 带 `_dy` 后缀**，写死的精确 id 一个都匹配不上。所以选择器用通配：

```js
'[id*="captcha"], [class*="tcaptcha"], iframe[src*="captcha"]'
```

### 陷阱二（最容易漏）：验证码过关后 DOM 还留着

**TCaptcha 验证通过后不删节点，只把父容器透明掉。** 实测祖先链：

```
IFRAME #tcaptcha_iframe_dy             opacity:1  visible  360×360   ← 自己看着是可见的
DIV    #tcaptcha_wrapper_transform_dy  opacity:0                     ← 真正藏起来的是父容器
BODY / HTML                            正常
```

如果你用 `document.querySelector(capSel)` 只判存在性，或者只检查节点自身的可见性——**验证码过完之后，页面会永远被判成 captcha，再也抓不了**，直到你重新加载页面。

所以必须**逐级向上遍历祖先**：

```js
for (var cur = node; cur; cur = cur.parentElement) {
  var s = getComputedStyle(cur);
  if (s.display === 'none' || s.visibility === 'hidden' || Number(s.opacity) === 0) return false;
}
```

### 陷阱三：验证码弹出前有一段「什么都看不出来」的窗口

实测：新开标签页后轮询 30 秒，状态一直是「页面没渲染好」；验证码在那之后**约 10 秒**才真正弹出来。

如果按「轮询若干次还不 ready 就判定被拦截」的规则，这里会误判成风控白屏，然后放弃——而真相只是验证码还没弹。

关键在于：**那 30 秒里信号其实已经在页面上了**——TCaptcha 的资源早已加载完，`window.TencentCaptcha` 已经是 `function`。所以：

```js
var capArming = typeof window.TencentCaptcha === 'function';
// loading 且 capArming 为 true → 验证码正在准备,要多等,别急着判定被拦截
```

## 四、一次群发 = 多篇文章

接口返回的结构是：

```
reviews[]            ← 一条 = 一次群发
  └─ subReviews[]    ← 一条 = 一篇文章
       └─ review.mpInfo.title / originalId
```

**只读 `subReviews[0]` 会丢掉同一次群发的其余文章。** 有的号一天群发 3–4 篇，只取第一篇会让你以为「这个号一天只发一篇」——作者就是这么误判的，直到有人说「我明明看到一天有好几篇」。

另外：**同一次群发里所有文章的 `createTime` 完全相同**。做增量时如果用「时间戳 > 上次最大值」筛选，这些同秒文章会在下一轮重复出现。按 `url` 或 `rid` 去重更稳。

## 五、翻页：只有 `offset` 有效

`/web/mp/articles` 默认返回**约 20 条群发**（展开后 70–80 篇）。想往回翻更旧的，只有一个参数管用。

### 三组同单位对照（实测 2026-08-11）

| 请求 | 群发条数 | 文章篇数 | 时间跨度 |
|---|---|---|---|
| `offset=0` | 20 | 74 | 相同 |
| `offset=0&count=50` | 20 | 74 | **逐字段一致** |
| `maxIdx=20` | 20 | 74 | **逐字段一致** |

**`count` 和 `maxIdx` 被服务端完全忽略。** 而 `offset` 是真的：`offset=20` 返回 07-21～07-02，和首页的 07-22 **无缝衔接**；`offset=74` 返回 05-28～05-09。所以工具只发 `offset`，一个字节的 `count` 都不发。

> ⚠️ 第三方项目 `weread.koplugin` 的源码里用的是 `maxIdx=0&count=100`。**二手来源只能当线索，不能当依据**——照抄它你会以为自己在翻页，其实每次都在拿第一页。

### 这里有一个值得记住的验证事故

作者第一次验证 `count=50` 时，是这么"确认它生效了"的：加了参数后拿到 **74 篇**，而印象中默认是 **20 条**——74 > 20，所以"生效了"。

**这是假阳性。** 20 是**群发条数**，74 是**文章篇数**，两个数字单位根本不同，74 篇本来就是 20 条群发展开的结果。加不加 `count` 拿到的是同一份数据。

> **判据**：验证一个参数"生效了"，必须**跑基线**（不加参数的那次）并且**同单位对比**。拿"加了之后的数"和"印象里的数"比，永远能比出你想要的结论。
>
> 现在工具把这条固化进了产物：`pageMeta` 逐页记 `{offset, reviews, items, oldest}`，同一次运行里三页的 `oldest` 必须**严格递减**——一次运行就能自证或自否，不用跨轮次去比。

### 翻页循环为什么放在 Node 侧而不是页内

早期版本把整个多号循环塞进一段注入 JS 里。改成 `--pages` 之后这条路走不通了：

| | 页内循环 | Node 侧循环（现在） |
|---|---|---|
| CDP 超时 | 4 号 × 10 页 × 3s = 117s，超过 `Runtime.evaluate` 的 90s 默认超时，得给 CDP 打动态超时补丁 | 每次 evaluate 只做一个 fetch，远低于 90s，`lib/cdp.mjs` 一行都不用动 |
| 部分失败 | 第 3 页失败时前 2 页的数据还在页内变量里，得靠额外契约带出来 | 前几页的结果已经在 Node 手上，部分失败是自然结果 |
| 可测试性 | 只能在 vm 里跑整段拼接脚本 | 翻页/去重/间隔/部分失败全是纯函数，用假 `run`、假 `sleep` 就能行为测试 |
| 代价 | — | 每页多一次 `Target.attachToTarget` / `detachFromTarget`。这是纯本地 CDP 往返，**不向微信读书发任何请求** |

代价那一栏值得说清楚：**它不提高请求速率**。间隔照样加在每两个请求之间（跨页也跨号），只是不再有"最后一个请求之后还傻等一轮"这种多余等待了。

### 去重键为什么是 `url || rid || null`

同一次群发里所有文章的 `createTime` **完全相同**（见上一节），所以**绝不能按时间戳去重**。而 `url` 和 `rid` 都**可能是空串**——`flatten` 只要求标题非空。用 `url || rid` 的话，这些条目会一起算出 `''`、塌缩成一条，**静默丢文章**。所以键为空时干脆不参与去重，原样保留。

## 六、限频：为什么做成硬闸门而不是写在文档里

作者在验证方案那天，一天内对文章接口请求了 30 多次，直接触发反爬，页面白屏好几个小时。

教训不是「要注意限频」，而是：**写在文档里的纪律约束不住人，也约束不住 AI**。当时那 30 多次，每一次单独看都有正当理由（调试、验证、复现），加起来就超了。

所以做成**执行前必须通过的闸门**，超限直接拒绝执行，而不是打印一句警告。

配套的几条：

- 每两个请求之间间隔 3 秒（跨页也跨号统一计，由调度器强制，不是调用方的自觉）
- 探针不消耗额度——让「先看看能不能抓」这件事零成本，否则人会为了省额度跳过检查
- 失败不记账，但**也不自动重试**

### 加了翻页之后：为什么是两道闸门而不是改一道

`--pages` 把单次运行的请求数从"号数"变成了"号数 × 页数"。这时候有个很自然但**错误**的念头：既然请求变多了，那就把额度改成按请求计费吧。

作者真这么干过一次，后果是：`maxRunsPerDay: 2` 的老配置语义突变，`--pages 3` 变成**永远被拒**——旧配置在新语义下自相矛盾，而用户对"我的额度花在哪"完全失去了预期。

所以现在是**两道独立的闸门**，老的那道一个字没改：

| 闸门 | 计什么 | 语义 |
|---|---|---|
| `maxRunsPerDay` | **运行次数** | 一次不算全败的运行 = 1 次。与最初完全一致 |
| `maxRequestsPerDay` | **真实请求数** | 纯增量的第二道。运行前按 `号数 × pages` 预估，不够就拒绝 |
| `maxPagesPerRun` | 单次运行的页数上限 | 超过直接拒绝，不截断 |

账本也从 `{date, count}` 扩成 `{date, count, requests:{articles, shelf}}`——一个数字没法审计"额度到底花在哪了"。老账本读进来缺的字段按 0 算，新账本被老代码读到时多余字段被忽略，两个方向都不会坏。

> ⚠️ `maxRequestsPerDay` 的默认值 40 是**选定值，不是实测出来的安全阈值**。唯一参照点是"一天 30 多个请求触发过一次反爬"这条一手观察——**一次观察不是阈值**，真实阈值未知也测不出来。
>
> `requests.shelf` 记的是**真实发出的书架请求**。最常见的来源不是出错路径，而是推导 `readerUrl`：没有可复用的阅读器标签页、config 里又没写 `readerUrl` 时，工具要问一次 `/web/shelf/sync` 才知道该打开哪个 URL——这 1 个请求会如实进账本，因而也占用 `maxRequestsPerDay` 的预算（运行前那句"预计 N 个请求"只按 `号数 × pages` 预估，不含它）。把阅读器标签页常开着，或者在 config 里写死 `readerUrl`，这个请求就不会发生。
>
> 一个已知的账本口径：**全部号都失败的那一轮不计账**（这是最初就有的语义，没动），所以那一轮发出去的请求（包括 `-2041` 出错路径上那 1 个书架探测）不会进账本。这是"保持记账语义不变"的代价，是知情的选择——两种书架请求一个记、一个不记，差别只在于**能不能走到记账那一行**。

## 七、少触发验证码：别反复新开标签页

实测结论：**短时间内用「新开标签页」的方式反复访问同一个阅读器页，会触发风控**——表现为白屏或弹验证码。同一时间用户手动访问完全正常，说明不是账号被封，是自动化访问模式被识别了。

取标签页的正确优先级：

1. **复用**已经打开、且标题含「公众号」的阅读器标签页
2. 没有就在**已有的微信读书标签页内导航**过去
3. 实在没有才新开，且同一个 URL 一天最多开一次

本工具默认走第 1 条，找不到才开新的，并且会提示你「之后别关它」。

## 八、连接 Chrome：为什么自己写 WebSocket

工具需要的能力只有一个：**在你已登录的 Chrome 标签页里执行 JS**。

没用 Puppeteer/Playwright，原因有两个：一是它们体积大（几百 MB），对一个几百行的小工具不成比例；二是它们常被风控识别成自动化浏览器。

CDP 的 `Runtime.evaluate` 只能走 WebSocket，没有纯 HTTP 的替代。而 Node 20 及更早没有全局 `WebSocket`，引入 `ws` 包又违背零依赖的初衷——所以 `lib/cdp.mjs` 里自己实现了一个最小 WebSocket 客户端（约 120 行，客户端帧掩码、分片重组、握手）。

另一个坑：`Target.createTarget` 会**立刻返回**，那一刻页面还停在 `about:blank`。不等它真正导航过去就执行 JS，拿到的是空白页——每个第一次使用、还没有阅读器标签页的人都会撞上。所以 `createTab` 里加了轮询等待。

### 端口发现：两条路，各自覆盖一种模式

> 以下均**实测于 2026-08-11，Chrome 151**。这一节的结论是**版本相关**的，Chrome 每 4 周一个大版本。

工具有两条发现端口/WebSocket 路径的路：读用户数据目录下的 `DevToolsActivePort` 文件（第 1 行端口、第 2 行浏览器级 WS 路径），以及 HTTP 探 `/json/version`。**它们不是"主路径 + 兜底"的关系，而是各管一种启动模式**：

| 模式 | `DevToolsActivePort` 文件 | `/json/version` | 实际走哪条 |
|---|---|---|---|
| 传统模式（`--remote-debugging-port` + 专用 `--user-data-dir`） | ❌ **不写**（Chrome 151 实测，有头/headless 都不写） | ✅ 200 | HTTP |
| auto-connect（`chrome://inspect` 里的 "Allow remote debugging for this browser instance"，Chrome ≥ 144） | ✅ 写（端口 + `/devtools/browser/<UUID>`） | ❌ **404** | 文件 |

也就是说，**推荐路径（专用 profile）实际走的是 HTTP 那条，文件那条根本拿不到**——早期文档写的"优先读文件、HTTP 只作兜底"在 Chrome 151 上已经与事实不符，这里更正。

另外三条同样是实测、同样会让人白花时间的：

- **Chrome 136（2025-04）起，在默认用户数据目录上 `--remote-debugging-port` 被静默忽略**（[官方说明](https://developer.chrome.com/blog/remote-debugging-port)）。端口不会开，**也不报错**。
- **端口冲突不报错**：9222 已被别的实例占用时，第二个实例静默退到 IPv6 `[::1]:9222`。此时 `curl http://127.0.0.1:9222/json/version` 打到的是**前一个**实例（返回 404），看起来像"端口开了但工具不认"。所以文档一律用 9333。
- **同一个 `--user-data-dir` 同时只能有一个 Chrome 进程**。目录已被占用时再带参数启动，只会打印「正在现有的浏览器会话中打开」并给旧进程开个新窗口，**新参数全部被静默忽略**。排查"参数没生效"时先查这条。

两条路都可能同时"有东西"，所以取值规则要写清楚：**`DevToolsActivePort` 文件里的 WebSocket 路径属于写这个文件的那个实例**。当你在配置里显式指定了 `chromePort`、而文件里记的是另一个端口时，这两样东西来自不同的浏览器实例——此时**以显式端口为准，丢弃文件里的 wsPath**，改走 HTTP 探测。（同机同时开着两个调试实例时才会遇到，比如日常 Chrome 开着 auto-connect 占 9222，另有一个专用实例在 9333。）配置 `chromeProfileDir` 指向你的专用目录，也能让工具只看那一个目录。

这条规则不是预防性的假设，**它修的是一个实测复现过的连接 bug**：早期版本里"取端口"和"取 wsPath"是两件互不相干的事——端口用你显式配置的那个，wsPath 却照单全收默认目录里读到的。于是「配置写 `chromePort: 9333` + 默认用户数据目录里躺着日常 Chrome（auto-connect）写下的 `9222` 与 `/devtools/browser/<UUID>`」这个组合下，工具会拿着**那个实例**的 wsPath 去连**另一个**端口，结果是**必然连不上**，而且失败得很没有信息量：握手阶段就被打回，报「Chrome 拒绝 WebSocket 升级」，看起来像端口或权限问题，实际两者都没错。现在的规则是**只有文件里的端口与显式端口一致时才采用文件里的 wsPath，否则丢弃、走 HTTP 探测**。实测于 2026-08-11 本机（Chrome 151）：同一环境下旧代码 0.0s 被拒，改后 0.1s 连接成功。

### 两条路的取舍：为什么默认推荐专用 profile

实测对照（2026-08-11，Chrome 151）：

| | 专用 profile（方案 A） | auto-connect（方案 B） |
|---|---|---|
| 建立连接 | 直接握手成功，**全程无授权弹窗** | **每次新连接都要人工点一次「允许」**：点了握手成功，两次实测分别是 **2.6s / 3.5s**（都含人在旁边看到弹窗再点下去的时间，所以这个数取决于人不取决于 Chrome）；不点则挂起（实测 60s、90s）；第二次连接不点仍挂起 12s → **授权不跨连接复用** |
| `/json/version` | 200 | 404 |
| 登录态 | 存在专用目录里，Chrome 完全退出后重启**仍保持登录** | 就是你日常那个 profile |
| 能否无人值守 | ✅ | ❌ |

结论：auto-connect 解决的是"既要默认 profile 又要开调试"，代价是每次连接都要人工确认——对一个命令行工具来说这个代价太大。所以默认推荐专用 profile，auto-connect 作备选并写明代价。这不是 Chrome 的缺陷，是它有意的安全设计，工具不去绕过。

## 九、这条路能撑多久

不知道。

2026 年 7 月底，微信在同一周收紧了多条第三方采集路线：公众平台后台的跨账号查询接口被关，一批开源项目同时失效，其中一个 12k+ star 的项目直接归档。微信读书这条路当时没受影响，但没有任何理由认为它一定长期有效。

**建议留降级方案**：比如同一条新闻从别的源也能覆盖到，别让整个流程只吊在这一根绳上。

## 十、怎么从零开始:bookId 和 readerUrl 都能自动拿到

新用户会卡在两个地方:**我怎么知道某个公众号的 bookId?** 和 **阅读器页 URL 从哪来?** 两个都有确定的答案,不需要手工翻。

### bookId:从任意一篇文章推导

`bookId = "MP_WXS_" + base64解码(__biz)`,而 `__biz` **明写在该公众号每一篇文章的页面里**——公开信息,不需要登录。

实测(2026-08-04):抓一篇文章页,正则取 `var biz = "MTIzNDU2Nzg5MA=="`,base64 解出 `1234567890`,拼成 `MP_WXS_1234567890` —— 与该号的真实 bookId **逐字符一致**。

顺便可以把号名也带出来,让用户确认加对了号。注意别取错字段:

| 字段 | 实际拿到 |
|---|---|
| `og:site_name` | 「微信公众平台」——固定值,不是号名 |
| `og:article:author` | 公众号简介,不是号名 |
| `nickname = htmlDecode("...")` | ✅ 号名 |
| `id="js_name"` 标签内容 | ✅ 号名 |

### 为什么不是「按名字搜索」

因为搜不到。实测这些全部无效:

| 尝试 | 结果 |
|---|---|
| `/web/search/global?keyword=` | 200,但只返回**书**,`MP_WXS_` 出现 0 次 |
| 加 `type=2` / `scope=2` / `mpOnly=1` | 响应与不加时**完全相同**,参数被忽略 |
| `/web/search/mp`、`/web/mp/search`、`/web/search/author` | 全部 404 |
| 微信读书官方 Agent Skill 搜公众号 | `-2041` |

响应里的 `parts` 字段看着像分类,其实只是查询词的分词结果（搜「某某公众号」返回 `["某某公众号","位","量子"]`），没用。

所以「给名字自动添加」这条路在微信读书侧走不通。**给文章链接是更可靠的替代**——链接在微信里长按就能复制。

### readerUrl:书架接口里就有

书架接口 `/web/shelf/sync` 每个条目都带 `deepLink`，形如：

```
https://weread.qq.com/book-detail?type=1&v=aaaaaa1224d505f5758535f31323334353637383930xx1
```

这个 `v` 和阅读器页 URL 尾部的 hash **完全相同**（实测逐字符比对一致）。所以：

```
readerUrl = "https://weread.qq.com/web/mp/reader/" + v
```

用户再也不用手动去地址栏复制。

### ⚠️ 那串 hash 不能自己拼

看到 `v = aaaaaa1 + hex('"' + bookId) + xx1` 这个结构，很容易想「那我照着给别的号拼一个不就行了」。**不行。** 前后缀是**每个号各不相同**的校验位：

| 公众号 | 前缀 | 后缀 |
|---|---|---|
| 甲 | `aaaaaa1` | `xx1` |
| 乙 | `bbbbbb2` | `xx2` |
| 丙 | `cccccc3` | `xx3` |
| 丁 | `ddddxx3` | `xx4` |

实测：拿甲的前后缀给乙拼出的 URL 打开是「加载失败，请点击重试」。老老实实从书架接口取。

### 哪些接口需要阅读器页上下文

不是所有接口都挑上下文。实测：

| 接口 | 微信读书首页 | 阅读器页 |
|---|---|---|
| `/web/shelf/sync`（书架） | ✅ 可用 | ✅ 可用 |
| `/mp/shelf/addToShelf`（订阅） | ✅ 可用 | ✅ 可用 |
| `/web/mp/articles`（**取文章**） | ❌ `-2041` | ✅ 可用 |

所以工具的流程是：先在任意 weread 页读书架拿到 readerUrl，再导航到阅读器页去抓文章。

> 补充：**取文章并不要求你订阅了这个号**——只要有 bookId 就能取。订阅只是为了让它出现在书架里、从而能拿到 readerUrl，以及方便 `--shelf` 列出来。

## 已知限制

| 限制 | 说明 |
|---|---|
| 收录不全 | 部分公众号在微信读书侧收录滞后，实测遇到过滞后半个多月的。平台侧问题，技术上无解 |
| 不实时 | 收录通常比公众号发布晚几个小时 |
| 登录要人工 | 扫码没法自动化，登录失效（`-2010`）后需要手动重新扫 |
| 规模有限 | 适合十几个以内的号。上百个号需要账号池加更严格的限频，不在本工具范围 |

## 错误码速查

| 返回 | 含义 | 处理 |
|---|---|---|
| 正常 JSON，含 `reviews` | 成功 | — |
| `-2041`，且页面正常渲染 | 成因不止一种：最常见的是请求发在了非阅读器页 | 工具会自动刷新一次阅读器页并重探，**只陈述观察不下结论**；探针报 `captcha` 就手动过一下再重跑 |
| `-2010 用户不存在` | 登录失效 | 重新扫码登录微信读书 |
| 探针报 `captcha` | 弹了验证码 | 手动完成后重跑 |
| 探针报 `blank` | 触发风控 | 停手，隔几小时再试，别反复新开标签页 |
| 空 `reviews` 但无错误码 | 该号在微信读书无收录 | 见「已知限制」 |
| **书架接口**返回 `errCode`（如 `-2041`/`-2010`） | 会话未续期或登录失效，**不是「书架是空的」** | 工具会明说是接口出错并给指引（-2010 重新扫码，其余先刷新页面）。只有接口正常、书架里确实没有公众号时，才提示 `--add`。曾有过的坑：出错被兜底成空数组，把登录态问题误诊成「你没订阅任何号」（2026-08-11 实测撞上，已修） |
